## 2026-11-16 · 安装后把 .md 关联到应用，双击打开不显示内容

- **状态**：已解决（M2-0，2026-11-16）
- **现象**：打包安装后，把 `.md` 的打开方式设为 Mile Typora，双击任意 Markdown 文件，应用启动但界面停在开始页，没有文档内容。应用已在运行时再双击另一个文件，同样没有内容。
- **影响**：文件关联是用户最自然的入口，现在等于不可用。P0 的"打开单个 Markdown 文件"因此在关联场景下不成立。
- **根因**：关联打开时，Windows 把文件路径作为命令行参数传给应用。当前实现只把参数放进窗口的打开请求队列（`enqueue`），页面收到后在状态栏显示"待打开：路径"，但**没有任何代码把请求变成实际打开**——请求到文档的接线原计划在 M2（`docs/开发计划.md` M1-2 卡片、M2-2 窗口行为矩阵）。M1-3 只实现了"系统对话框选文件"这一条入口。
- **临时对策**：应用内用工具栏"打开文件"（`Ctrl+O`）选择该文件，可以正常阅读。
- **处理**（M2-0）：
  1. 页面拿到打开请求后调用一个新的绑定方法，把请求里的路径交给 Go 读取、渲染并返回文档；
  2. 授权口径：命令行参数与文件关联属于用户对这份文件的明确意图，与对话框选择同等对待；仍要过真实路径、重解析点、容量与编码检查；
  3. 第二个实例传来的路径交给有焦点的窗口，并在该窗口打开；
  4. 打开失败（文件不存在、编码不对）时在窗口内提示，不是停在开始页；
  5. 验收：安装包关联 `.md` 后双击能读到内容；应用已运行时双击第二个文件能切换；双击不存在的文件有明确提示。
- **结果**：页面收到打开请求后调用 `OpenRequested(seq)`，Go 按请求里的路径读取、渲染并把文档返回；同一个请求重放时返回窗口当前文档（页面重挂载不会丢）。原生验证：带路径启动直接显示 `gfm.md`（h1 与 5 个 h2 都在）；带不存在路径显示"文件不存在或已被移动"；带 `package.json` 显示"只支持 .md 和 .markdown 文件"。
- **教训**：入口与投递链路要一起验收。M1-2 只验了"请求送达页面"，没验"请求变成可读的文档"，用户一装就踩到。

## 2026-11-16 · 命令行传入目录时按文件打开，提示"只支持 .md 和 .markdown 文件"

- **状态**：未处理（记录，P0 无此入口要求）
- **现象**：以目录作为命令行参数启动（例如 `Mile Typora Dev.exe testdata/tree`），窗口显示"无法打开文件 / 只支持 .md 和 .markdown 文件"，没有打开文件树。
- **根因**：`main.go` 的 `enqueue` 把 `os.Args` 里的每一项都当作文件请求（`winctx.KindFile`）；只有启动恢复的目录请求走 `enqueueKind(..., KindFolder, ...)`。`openPath` 对目录自然报 `unsupported_type`。
- **影响**：只影响"把目录拖到 exe / 命令行传目录"这种非 PRD 入口；文件关联与对话框打开目录不受影响。M3-4 的原生"移除根目录"用例因此改在后续阶段用对话框验证。
- **可能的处理**：`enqueue` 对每项 `os.Stat`，目录走 `KindFolder`；需要在 PRD 的入口清单里先确认是否支持这一种启动方式（目前 FR-02 只写文件关联）。
